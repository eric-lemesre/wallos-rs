# Relecture REQ-SUB-002 — Création d'abonnement

**Date** : 2026-07-28  
**Périmètre** : `crates/storage/src/subscriptions.rs`, `crates/storage/migrations/0007_subscriptions.sql`, `crates/proto/src/lib.rs` (`CreateSubscriptionRequest`, `FieldError`, `SubscriptionDto.next_payment`, `from_core_with_next_payment`), `crates/server/src/subscriptions.rs`, `crates/server/tests/subscriptions.rs`.  
**Référentiel** : AGENTS.md §0/§6/§9, `spec/requirements/subscriptions.md` (REQ-SUB-002), ADR 0006, ADR 0012, ADR 0022.  
**Auteur relecture** : relecteur Rust senior critique.

---

## Résumé

L'implémentation respecte l'architecture cible : `core` reste pur, le repository filtre bien par `household_id`, la validation par champ est en place, les montants transitent en `Decimal`/chaîne (R4) et le calcul d'échéance suit l'ancrage+clamp de l'ADR 0022.  
Cependant, plusieurs défauts de robustesse et de couverture des tests empêchent de valider l'exigence comme *terminée* sans correction :

- un **clamp silencieux** dans le mapping `u32 → i32` du cycle d'abonnement, qui corromprait la donnée persitée pour un intervalle hors plage SQL ;
- les **tests d'autorisation §9** sont formels mais ne vérifient pas l'isolation *cross-household* réelle ;
- le **test fonctionnel** ne contrôle pas que l'abonnement a bien été persisté ;
- plusieurs **chemins de validation** (unité inconnue, intervalle 0, UUID optionnel invalide, nom vide, date invalide) ne sont pas couverts.

## Findings

### CRITICAL

#### CRIT-1 — Corruption silencieuse de `cycle_interval` si `interval > i32::MAX`

- **Fichier:ligne** : `crates/storage/src/subscriptions.rs:79`
- **Code** :
  ```rust
  .bind(i32::try_from(sub.cycle().interval()).unwrap_or(i32::MAX))
  ```
- **Défaut** : le domaine expose `cycle.interval()` comme `u32`, la colonne SQL est `integer` (`i32`). Au lieu de rejeter une valeur hors plage, le code la remplace silencieusement par `i32::MAX`. C'est une corruption de donnée : l'abonnement est créé avec un cycle différent de celui demandé, et l'appelant reçoit un `201 Created` sans aucune indication d'erreur.
- **Scénario d'échec** :
  ```json
  { "cycle": { "unit": "day", "interval": 3000000000 }, ... }
  ```
  Le domaine accepte `interval = 3_000_000_000`. Le repository le clampe à `2_147_483_647` avant insertion. La base contient une valeur incorrecte ; le calcul de `next_due` en lecture retournera `None` (overflow / `MAX_STEPS`) et l'abonnement apparaîtra comme « échéance hors plage ».
- **Correctif** :
  - Option A (préférée) : valider dans `CreateSubscriptionRequest::into_core` que `cycle.interval <= i32::MAX as u32` et renvoyer un `FieldError` sur `cycle.interval`.
  - Option B : élargir la colonne SQL à `bigint` pour refléter le type domaine `u32`.
  - Dans les deux cas, interdire le clamp silencieux en production.

### HIGH

#### HIGH-1 — Test `authz_other_create_subscription` ne vérifie pas l'isolation

- **Fichier:ligne** : `crates/server/tests/subscriptions.rs:151-160`
- **Code** :
  ```rust
  async fn authz_other_create_subscription(pool: PgPool) {
      let web = account(&pool, "other-sub@example.com").await;
      assert_eq!(
          create(&pool, &web, valid_body()).await.status(),
          StatusCode::CREATED
      );
  }
  ```
- **Défaut** : ce test crée un second compte dans un second foyer et constate qu'il peut créer son propre abonnement (`201`). Cela ne teste **aucune** isolation : il ne tente pas d'accéder à une ressource du foyer A depuis le foyer B, et comme `POST /subscriptions` ne prend pas d'identifiant de ressource cible, le scénario « other 404 » n'a pas de sens ici. Le test est donc trompeur et ne satisfait pas l'esprit d'AGENTS.md §9 (trois tests par opération : owner 2xx / other 404 / anon 401).
- **Scénario d'échec** : si un futur endpoint `GET /subscriptions/{id}` oubliait la clause `household_id`, ce test ne le détecterait pas.
- **Correctif** : soit supprimer ce test factice pour `createSubscription` (l'isolation se testera sur la lecture), soit — si l'on veut vraiment un test cross-household dès maintenant — créer un abonnement avec le compte A, puis tenter de le lire avec le compte B et vérifier le `404` (nécessite l'endpoint de lecture, hors périmètre). En attendant, le test actuel doit être au minimum renommé et commenté comme *smoke* de création, pas comme test d'isolation.

#### HIGH-2 — Le test fonctionnel ne vérifie pas la persistance réelle

- **Fichier:ligne** : `crates/server/tests/subscriptions.rs:90-104`
- **Code** :
  ```rust
  async fn creates_subscription_with_next_payment(pool: PgPool) {
      let web = account(&pool, "sub@example.com").await;
      let r = create(&pool, &web, valid_body()).await;
      assert_eq!(r.status(), StatusCode::CREATED);
      let body = body_json(r).await;
      // ... assertions sur la réponse
  }
  ```
- **Défaut** : le test s'arrête à la réponse HTTP. Il ne relit pas la ligne en base (via `SubscriptionRepository::get` ou un endpoint GET) pour vérifier que tous les champs ont bien été persistés avec le bon `household_id`.
- **Scénario d'échec** : un handler qui renverrait `201` sans jamais appeler `repo.create()`, ou qui tronquerait silencieusement certains champs, ferait passer le test.
- **Correctif** : après le `201`, appeler `SubscriptionRepository::new(db.pool()).get(&actor, id)` et vérifier que `name`, `amount`, `currency`, `cycle_unit`, `cycle_interval`, `first_payment`, `household_id` correspondent.

#### HIGH-3 — Couverture de validation incomplète

- **Fichier** : `crates/server/tests/subscriptions.rs`
- **Défaut** : seuls deux cas de validation par champ sont testés (`amount` négatif, `currency` inconnue). Les chemins suivants, pourtant implémentés dans `CreateSubscriptionRequest::into_core`, ne le sont pas :
  - `cycle.unit` inconnu (`"fortnight"`) ;
  - `cycle.interval == 0` ;
  - `first_payment` mal formé (`"31/01/2026"`) ;
  - `category` / `payment_method` / `payer` avec un UUID invalide ;
  - `name` vide (renvoie `FieldError("name", ...)`).
- **Scénario d'échec** : une régression dans `BillingUnit::parse`, `BillingCycle::from_parts` ou `parse_optional_uuid` pourrait ne pas être détectée.
- **Correctif** : ajouter un test par champ fautif, en vérifiant à la fois le statut `422` et le nom du champ dans `detail`.

### MEDIUM

#### MED-1 — Mapping trompeur quand `next_due` retourne `None`

- **Fichier:ligne** : `crates/server/src/subscriptions.rs:55-65`
- **Code** :
  ```rust
  let reference = today.pred_opt().unwrap_or(today);
  let Some(next) = next_due(
      subscription.first_payment(),
      subscription.cycle(),
      reference,
  ) else {
      return field_error(&FieldError::new("first_payment", "échéance hors plage"));
  };
  ```
- **Défaut** : `next_due` peut retourner `None` pour deux raisons très différentes : (a) la date de référence ou l'ancre est hors plage représentable, ou (b) la borne `MAX_STEPS` est atteinte à cause d'un `cycle.interval` extrême. Dans le cas (b), l'erreur est attribuée à `first_payment`, ce qui est faux et oriente l'utilisateur vers le mauvais champ.
- **Scénario d'échec** :
  ```json
  { "cycle": { "unit": "day", "interval": 200000 }, "first_payment": "2026-01-01" }
  ```
  `next_due` atteint `MAX_STEPS` (100 000 occurrences ≈ 273 ans) et renvoie `None`. L'API répond `422` avec `detail: "first_payment: échéance hors plage"` alors que le champ fautif est `cycle.interval`.
- **Correctif** : après validation de `cycle.interval` (voir CRIT-1), s'assurer que seuls les cas de date hors plage aboutissent à `first_payment`. Pour les intervalles extrêmes, renvoyer un `FieldError` sur `cycle.interval` (par exemple en vérifiant a priori que `interval` n'entraînera pas un rattrapage démesuré).

#### MED-2 — Duplication de la logique de validation entre DTO et requête

- **Fichier** : `crates/proto/src/lib.rs:378-415` (SubscriptionDto::into_core) et `crates/proto/src/lib.rs:464-507` (CreateSubscriptionRequest::into_core)
- **Défaut** : les deux méthodes répètent presque exactement le même code de parsing/validation (`amount`, `currency`, `BillingUnit::parse`, `BillingCycle::from_parts`, `NaiveDate::parse_from_str`, `parse_optional_uuid`). Toute évolution future (normalisation du nom, nouvelle règle de devise, etc.) risque d'être appliquée à l'une et oubliée à l'autre.
- **Scénario d'échec** : un correctif sur la validation de `CreateSubscriptionRequest` n'est pas automatiquement reporté sur `SubscriptionDto::into_core`, utilisé par la mise à jour (REQ-SUB-004 future), ce qui introduit une divergence de contrat.
- **Correctif** : factoriser la validation dans une fonction interne commune, par exemple :
  ```rust
  fn validate_subscription_parts(
      amount: &str, currency: &str, cycle: &BillingCycleDto, first_payment: &str,
  ) -> Result<(Money, BillingCycle, NaiveDate), FieldError> { ... }
  ```
  et l'appeler depuis les deux `into_core`.

#### MED-3 — Le nom n'est pas normalisé (espaces de bord)

- **Fichier:ligne** : `crates/proto/src/lib.rs:480-481`
- **Code** :
  ```rust
  let mut sub = Subscription::new(id, self.name, price, cycle, first_payment)
      .map_err(|_| FieldError::new("name", "nom obligatoire"))?;
  ```
- **Défaut** : `Subscription::new` rejette un nom vide après `trim()`, mais il stocke la chaîne telle quelle. Un nom `"  Netflix  "` est donc accepté et persisté avec ses espaces, contrairement aux catégories (`CreateCategoryRequest`) qui documentent une normalisation des espaces de bord.
- **Scénario d'échec** : deux abonnements `"Netflix"` et `"  Netflix  "` coexistent, ou la recherche/sérialisation devient incohérente.
- **Correctif** : normaliser le nom (`trim()` et/ou refuser les espaces de bord) dans `CreateSubscriptionRequest::into_core`, ou au moins dans `Subscription::new`.

### LOW

#### LOW-1 — `FieldError` n'autorise pas de message contextuel

- **Fichier:ligne** : `crates/proto/src/lib.rs:510-525`
- **Défaut** : `FieldError` utilise des `&'static str` pour `field` et `message`. Cela empêche d'inclure la valeur fautive dans le message (par exemple `"montant invalide: foo"`), ce qui réduit la valeur du diagnostic pour le front.
- **Correctif** : passer `field` et `message` à `String` (ou `Cow<'static, str>`) si l'on souhaite enrichir les messages sans allocation systématique.

#### LOW-2 — Type URI RFC 9457 générique (`about:blank`)

- **Fichier:ligne** : `crates/server/src/subscriptions.rs:23-29`
- **Défaut** : les erreurs de validation renvoient `type: "about:blank"`. Bien que conforme à la RFC, le contrat de l'API gagnerait à exposer un type stable (par exemple `https://api.wallos.rs/errors/validation`) pour que le client puisse identifier programmatiquement une erreur de validation sans parser `title`.
- **Correctif** : introduire une constante ou une fonction `problem::validation()` renvoyant un `type_uri` stable.

#### LOW-3 — Aucune limite de taille sur les champs texte libres

- **Fichier** : `crates/proto/src/lib.rs:420-456` (`CreateSubscriptionRequest`)
- **Défaut** : `name`, `logo`, `url`, `notes` n'ont pas de `max_length` côté schéma OpenAPI ni de validation côté serveur. La colonne SQL étant `text`, un client malveillant peut stocker des méga-octets dans ces champs.
- **Correctif** : ajouter des `max_length` dans les annotations `#[schema(...)]` et une validation côté serveur (par exemple `name.len() <= 255`, `notes.len() <= 10_000`).

### NIT

#### NIT-1 — Absence de contrainte `CHECK` sur `cycle_interval`

- **Fichier:ligne** : `crates/storage/migrations/0007_subscriptions.sql:12`
- **Défaut** : la colonne `cycle_interval integer not null` n'a pas de `check (cycle_interval > 0)`. La validité repose entièrement sur `core`.
- **Justification** : acceptable car `core` garantit `NonZeroU32`, mais une contrainte SQL serait une défense en profondeur.
- **Correctif** (optionnel) : `cycle_interval integer not null check (cycle_interval > 0)`.

#### NIT-2 — Chemin OpenAPI sans préfixe explicite

- **Fichier:ligne** : `crates/server/src/subscriptions.rs:34`
- **Défaut** : `path = "/subscriptions"` ne mentionne pas `/api/v1`. Le nest dans `app_with_db` rajoute le préfixe, mais la spécification OpenAPI générée indiquera `/subscriptions` si `servers` n'est pas pris en compte.
- **Correctif** : s'assurer que `api/openapi.json` reflète bien `/api/v1/subscriptions` (vérifié par `cargo xtask openapi --check`).

## Vérifications positives

- **Isolation repository** : `create` et `get` filtrent bien par `household_id` (`crates/storage/src/subscriptions.rs:66-91` et `crates/storage/src/subscriptions.rs:98-113`). Pas de méthode publique sans `&Actor`.
- **R4 (montants)** : `amount` est `Decimal` dans `core`, chaîne dans l'API, `numeric` en base. Aucun `f32`/`f64`.
- **R5 (pas de panic)** : les seuls `unwrap`/`expect` sont dans `#[cfg(test)]`. Les `unwrap_or` en production sont acceptables syntaxiquement mais voir CRIT-1 pour le problème sémantique.
- **Calcul d'échéance** : utilisation correcte de `pred_opt()` pour obtenir une échéance ≥ aujourd'hui, et appel à `next_due` avec l'horloge injectée côté serveur (`Utc::now()`).
- **Mapping DTO** : `from_core_with_next_payment` enrichit correctement le DTO sans muter le modèle domaine.

---

## Verdict

**Rejeté en l'état pour la fusion sur `main`, malgré l'architecture globalement correcte.**

Les défauts **CRIT-1** (corruption silencieuse de données) et **HIGH-1/HIGH-2/HIGH-3** (tests d'autorisation et de persistance insuffisants) sont bloquants au regard d'AGENTS.md §0 (règles non négociables) et §9 (isolation).  
**À corriger avant validation** :

1. interdire `cycle.interval > i32::MAX as u32` dans `CreateSubscriptionRequest::into_core` ;
2. renommer/supprimer le test `authz_other_create_subscription` ou le remplacer par un vrai test cross-household dès que la lecture est disponible ;
3. vérifier la persistance en base dans `creates_subscription_with_next_payment` ;
4. compléter la couverture des cas de validation par champ.

Les findings **MED-1 à MED-3** doivent être traités dans le même commit atomique ou immédiatement après. Les findings LOW/NIT peuvent faire l'objet de corrections séparées mais ne doivent pas être oubliés.
