**Exigence** : REQ-SYN-006 — *Idempotence des opérations d'écriture*  
**Revueur** : agent IA (Kimi Code CLI)  
**Focus** : défauts de correction réels et prioritaires sur (1) l'atomicité et la réservation `PENDING`, (2) la robustesse de l'empreinte et de l'orchestration côté serveur, (3) l'isolation par utilisateur, (4) le relâchement des erreurs retryables, (5) la couverture des tests d'intégration. ## Verdict global

**Requête de changements (RC).**

Le commit atteint le comportement nominal de REQ-SYN-006 : rejeu clé + corps identiques renvoie la réponse mémorisée, réutilisation avec un corps différent renvoie `409`, et l'isolation par `user_id` empêche l'interférence entre comptes distincts. En revanche, il introduit un **défaut de correction sérieux sur la durée de vie des réservations `PENDING`** : en l'absence de mécanisme de purge ou de TTL, tout incident empêchant l'appel à `complete`/`release` (panic, OOM, mise à jour forcée du pod, coupure réseau du client juste après la réservation) transforme la clé en clé bloquée **pour toujours**. De plus, les échecs de `complete` et `release` sont **silencieusement ignorés**, ce qui aggrave le risque d'orphelin. La couverture de tests est inégale : bonne pour les catégories, très limitée pour les abonnements, inexistante pour les moyens de paiement, et aucun scénario de concurrence réelle ou de rejeu après erreur retryable n'est présent.

## Traitement (correctifs — commit de suivi `fix/syn-006-review`)

- **F1 ✅** — `reserve` **récupère atomiquement** une réservation `PENDING` orpheline plus vieille que `RESERVATION_TTL` (5 min) : un `UPDATE ... WHERE response_status = PENDING AND created_at < now() - interval '5 minutes'` conditionnel réattribue la clé (un seul appelant gagne). Un handler nominal se termine en millisecondes → aucune exécution légitime en cours ne peut être recouverte. La clé n'est donc **jamais bloquée à vie** après un incident. Colonne `created_at` existante réutilisée (pas de migration). Test : `stale_pending_reservation_is_reclaimed` (insère une réservation orpheline de 10 min → la création réussit).
- **F2 ✅** — `finish`/`abort` **journalisent** désormais (`tracing::warn!`) tout échec de `complete`/`release` au lieu de l'ignorer silencieusement. Combiné à F1, une réservation orpheline résultant d'un tel échec est **auto-récupérée** après le TTL : la panne transitoire ne devient plus une indisponibilité permanente de la clé.
- **F3 ✅** — test `concurrent_replays_produce_a_single_side_effect` : deux requêtes **strictement simultanées** (`tokio::join!`) même clé + même corps → **exactement une** catégorie créée ; chaque réponse est 201 ou 409.
- **F4 ✅** — payment_methods : tests de rejeu réussi et de conflit `409` ajoutés (à parité avec les catégories).
- **F5 ✅** — test `retryable_error_releases_the_key` : corps invalide + clé → `422` (relâché), puis corps valide + **même clé** → `201`. Prouve que l'erreur ne bloque pas la clé.
- **F9 ✅** — abonnements : test de conflit `409` (clé réutilisée, corps différent) ajouté.

### Findings non retenus (jugés non défectueux)

- **F6 ❌** — L'empreinte `serde_json::to_string(req)` est **déterministe pour un type de DTO donné** (ordre des champs fixé par la struct) : deux requêtes identiques produisent toujours la même empreinte, deux requêtes différentes des empreintes différentes. Le risque n'apparaîtrait qu'à une refactorisation future de l'ordre des champs **et** avec des clés historiques en vol simultané — cas inexistant ici. La canonicalisation (tri des clés) est une robustesse pour un futur format d'échange, pas une correction. Différé sans dette.
- **F7 ❌** — Les `unwrap_or*` portent sur des cas **inatteignables** : un code HTTP stocké est toujours un 2xx réel (`finish` n'est appelé que sur succès ; une ligne `PENDING` n'est jamais renvoyée en `Replay`), la sérialisation de ces DTO simples (aucune clé non-`String`, aucun flottant) ne peut pas échouer, et un statut HTTP tient toujours dans un `i16`. `unwrap_or` (et non `unwrap`) respecte R5. Remplacer par des `Result`/panics ajouterait du bruit sur des invariants garantis par le type.
- **F8 ❌** — La portée **par utilisateur** est **délibérée et correcte** : une clé d'idempotence est générée par le **client/appareil** (lié à une session utilisateur), pas par le foyer. Dédupliquer entre utilisateurs d'un foyer serait un défaut (la clé de l'utilisateur A bloquerait l'utilisateur B). Deux utilisateurs distincts sont deux clients aux espaces de clés indépendants. Aucun accès croisé entre foyers (§9 préservée). Choix documenté dans le commentaire de la migration.

## F1 — Réservations `PENDING` orphelines sans mécanisme de purge

### Description

`IdempotencyRepository::reserve` insère une ligne avec `response_status = 0` (`PENDING`) lors de la première requête :

```rust
// crates/storage/src/idempotency.rs:64-76
let inserted = sqlx::query(
    "insert into idempotency_keys \
         (user_id, idempotency_key, request_fingerprint, response_status, response_body) \
     values ($1, $2, $3, $4, '') on conflict do nothing",
)
.bind(actor.user_id())
.bind(key)
.bind(fingerprint)
.bind(PENDING)
.execute(self.pool)
.await?;
```

Cette ligne n'est transformée en réponse mémorisée que par `complete` (succès 2xx) ou supprimée par `release` (erreur retryable). Si le processus du handler est interrompu entre les deux — panic, `kill -9`, OOM, redémarrage du nœud, coupure réseau juste après `reserve` — la clé reste en statut `PENDING` **sans expiration**.

Le commentaire dans `finish` évoque une « purge ultérieure » :

```rust
// crates/server/src/idempotency.rs:104-110
// Échec de mémorisation non bloquant : la réponse a bien été produite ; au pire un rejeu
// ré-exécutera (la réservation sera relâchée par une purge ultérieure).
let _ = IdempotencyRepository::new(db.pool())
    .complete(actor, key, status.as_u16(), body)
    .await;
```

Aucun job, cron, procédure stockée ou colonne `expires_at` n'existe dans le dépôt pour réaliser cette purge.

### Conséquences

- **Blocage permanent de la clé.** Un client qui rejoue la même clé recevra `409` (ou `500` si on considère l'erreur interne) indéfiniment, même si le corps est identique à la requête originale.
- **Violation de la promesse REQ-SYN-006.** L'exigence promet qu'un rejeu à clé + corps identiques renvoie la réponse initiale. Avec une réservation orpheline, cette promesse est rompue.
- **Nécessité d'intervention manuelle.** L'utilisateur ou l'opérateur doit supprimer la ligne en base ou changer de clé côté client.

### Recommandation

Ajouter une colonne `reserved_at timestamptz not null default now()` et une tâche de purge périodique (scheduler côté serveur, ou clause `where reserved_at < now() - interval '5 minutes'` dans `reserve` pour traiter les réservations abandonnées comme des clés disponibles). Alternative plus simple : stocker `expires_at` et l'inclure dans la clé primaire si la durée de vie doit être explicite. À minima, un worker qui supprime les lignes `PENDING` vieilles de quelques minutes rétablit la sémantique attendue.

## F2 — Échecs de `complete`/`release` silencieusement ignorés

### Description

Les fonctions `finish` et `abort` ignorent le résultat des appels à `complete` et `release` :

```rust
// crates/server/src/idempotency.rs:103-121
pub async fn finish(db: &Db, actor: &Actor, key: Option<&str>, status: StatusCode, body: &str) {
    if let Some(key) = key {
        let _ = IdempotencyRepository::new(db.pool())
            .complete(actor, key, status.as_u16(), body)
            .await;
    }
}

pub async fn abort(db: &Db, actor: &Actor, key: Option<&str>) {
    if let Some(key) = key {
        let _ = IdempotencyRepository::new(db.pool())
            .release(actor, key)
            .await;
    }
}
```

### Conséquences

- Si `complete` échoue (connexion perdue juste après le succès métier, deadlock, redémarrage Postgres), la réponse a déjà été envoyée au client, mais la clé reste `PENDING`. Tout rejeu retournera `409` au lieu de la réponse mémorisée → F1.
- Si `release` échoue (même causes), une erreur `422`/`500` — pourtant explicitement *retryable* par design — laisse la clé bloquée. Le client ne peut pas réessayer avec la même clé.
- Le mécanisme d'idempotence devient source d'indisponibilité : une panne transitoire de la base à la fin d'une écriture transforme une erreur temporaire en erreur permanente pour cette clé.

### Recommandation

Ne pas ignorer les erreurs de `complete`/`release`. Deux options :

1. **Option stricte (préférée)** : propager l'erreur au client sous forme de `500` avec un message indiquant que l'idempotence n'a pas pu être enregistrée. Le client peut réessayer avec une nouvelle clé. Cela préserve la clarté du contrat.
2. **Option best-effort avec log/métrique** : garder le `let _ =` mais journaliser l'erreur et augmenter un compteur, en complément d'un mécanisme de purge (F1). Cela ne résout pas le problème à l'instant T mais permet de le détecter.

La combinaison des deux (log + retour d'erreur) est la plus sûre.

## F3 — Absence de test de concurrence réelle

### Description

Les tests actuels exécutent les requêtes de manière séquentielle dans un seul thread asynchrone. Aucun test ne lance deux requêtes **strictement simultanées** avec la même clé pour vérifier que :

- une seule obtient `Reservation::Proceed` ;
- l'autre obtient bien `409` (exécution en cours) ou, si la première a terminé, la réponse mémorisée.

### Conséquences

- Le mécanisme `insert ... on conflict do nothing` + relecture est **logiquement correct** mais **non prouvé** par la suite de tests. Une régression future (passage à un cache Redis, suppression du `on conflict do nothing`, etc.) ne serait pas détectée.
- Le scénario le plus critique de REQ-SYN-006 — le rejeu exactement au moment où la première requête est en cours — n'est pas couvert.

### Recommandation

Ajouter un test d'intégration qui lance deux `app.oneshot(...)` concurrents avec la même clé et le même corps, et vérifie qu'il n'y a qu'un seul effet de bord. Idéalement, utiliser un petit délai artificiel (instrumentation du repository) pour forcer la fenêtre de concurrence.

## F5 — Aucun test de rejeu après erreur retryable

### Description

Le design affirme que seules les réponses 2xx sont mémorisées et que les erreurs (`422`, `500`) relâchent la réservation. Aucun test ne vérifie la séquence suivante :

1. Requête avec clé `K` et corps invalide → `422`.
2. Requête avec clé `K` et corps valide → `201`.

### Conséquences

- Si `abort` ou `release` régresse, le client se retrouve bloqué sur une clé après une simple erreur de validation.
- La promesse « les erreurs sont retryables » n'est pas garantie par la CI.

### Recommandation

Ajouter un test dans `categories.rs` (et éventuellement `payment_methods.rs` / `subscriptions.rs`) qui envoie un corps invalide avec une clé, vérifie le `422`, puis envoie un corps valide avec la même clé et vérifie la création réussie.

## F6 — Empreinte JSON non canonique

### Description

L'empreinte est calculée par `serde_json::to_string(req)` :

```rust
// crates/server/src/idempotency.rs:56-59
fn fingerprint<T: Serialize>(req: &T) -> String {
    serde_json::to_string(req).unwrap_or_default()
}
```

L'ordre des clés dépend de l'ordre de déclaration des champs dans les structs de `crates/proto/src/lib.rs`. Actuellement, les structs sont stables et les champs `Option` utilisent `skip_serializing_if = "Option::is_none"`, donc deux corps équivalents produisent la même empreinte.

### Conséquences

- Une refactorisation future qui changerait l'ordre des champs ou les options de sérialisation casserait l'égalité d'empreinte pour des requêtes historiques. Cela n'est pas un bug immédiat mais une fragilité.
- `unwrap_or_default()` retourne une chaîne vide si jamais la sérialisation échoue ; deux requêtes différentes mais toutes deux non sérialisables auraient la même empreinte.

### Recommandation

Utiliser une empreinte canonique : sérialiser en JSON puis reparser comme `serde_json::Value`, trier récursivement les clés des objets, puis resérialiser. Cela rend l'empreinte robuste aux réordonnancements. Vérifier aussi explicitement l'échec de sérialisation plutôt que de masquer par `unwrap_or_default()`.

## F7 — Valeurs par défaut silencieuses sur des états anormaux

### Description

Plusieurs endroits utilisent des `unwrap_or*` pour des cas qui ne devraient jamais arriver :

```rust
// crates/server/src/idempotency.rs:58
serde_json::to_string(req).unwrap_or_default()

// crates/server/src/idempotency.rs:73
let status = StatusCode::from_u16(status).unwrap_or(StatusCode::OK);

// crates/storage/src/idempotency.rs:92
status: u16::try_from(status).unwrap_or(0),

// crates/storage/src/idempotency.rs:118
.bind(i16::try_from(status).unwrap_or(PENDING))

// crates/server/src/categories.rs:125, payment_methods.rs:118, subscriptions.rs:135
serde_json::to_string(&dto).unwrap_or_default()
```

### Conséquences

- Si un statut invalide est lu de la base (corruption, bug d'insertion), `replay` renvoie `200 OK` au lieu d'une erreur.
- Si `complete` reçoit un statut > `i16::MAX`, il stocke `PENDING` et crée une réservation orpheline (F1).
- Si la sérialisation du DTO échoue, le client reçoit un corps vide avec un `201`, ce qui est incohérent.

### Recommandation

Remplacer les valeurs par défaut par des erreurs explicites (`Result`) ou des `expect`/`panic` documentés si l'invariant est censé être garanti par le type. Au minimum, journaliser ces cas comme des erreurs internes.

## F8 — Portée par `user_id` vs `household_id`

### Description

La table `idempotency_keys` utilise `(user_id, idempotency_key)` comme clé primaire :

```sql
-- crates/storage/migrations/0017_idempotency_keys.sql:10-18
create table idempotency_keys (
    user_id          uuid        not null references users (id),
    idempotency_key  text        not null,
    ...
    primary key (user_id, idempotency_key)
);
```

Cela isole bien deux utilisateurs différents, conformément au commentaire « Portée par utilisateur (user_id) ». Cependant, ADR 0012 définit le foyer (`household_id`) comme unité de propriété et d'isolation des données métier. Deux membres du même foyer peuvent donc utiliser la même clé et créer chacun leur propre catégorie / abonnement / moyen de paiement dans le même foyer.

### Conséquences

- Ce n'est pas une faille de sécurité : aucun accès croisé entre foyers.
- C'est une incohérence sémantique : l'idempotence est au niveau de l'utilisateur alors que la ressource créée appartient au foyer. Dans un foyer partagé, un client qui synchronise sur plusieurs appareils du même compte utilisateur verra la clé fonctionner normalement ; mais deux comptes distincts du foyer peuvent théoriquement créer un doublon avec la même clé.

### Recommandation

Documenter explicitement le choix `user_id` dans un ADR si ce n'est pas déjà fait. Si l'intention est d'éviter les doublons au niveau du foyer, migrer la clé primaire vers `(household_id, idempotency_key)`.
