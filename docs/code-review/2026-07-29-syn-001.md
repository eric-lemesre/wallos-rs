## Verdict global

**Requête de changements (RC).**

Le commit atteint son objectif fonctionnel de base : les UUID fournis par le client sont conservés à la création et `updated_at` est bien posé par l'horloge serveur. Cependant, il introduit un **défaut de correction réel dans la gestion des collisions d'unicité pour les catégories** : toute violation d'unicité (clé primaire `id` ou index unique sur le nom) est traduite par un message « nom déjà utilisé dans ce foyer », ce qui est faux quand la collision porte sur l'`id`. Cela crée une fuite d'existence cross-foyer théorique et une mauvaise expérience utilisateur. Les tests de timestamp sont également **fragiles** (flakiness probable en CI). Les erreurs 500 sur `id` déjà existant pour moyens de paiement et abonnements doivent être adoucies en erreur client.

## F1 — Catégories : une violation d'unicité sur l'`id` client est faussement signalée comme doublon de nom

### Description

`CategoryRepository::create` capture **toute** erreur `is_unique_violation` et la transforme en `Ok(false)` :

```rust
// crates/storage/src/categories.rs:57-70
pub async fn create(&self, actor: &Actor, id: Uuid, name: &str) -> Result<bool, StorageError> {
    let inserted =
        sqlx::query("insert into categories (id, household_id, name) values ($1, $2, $3)")
            .bind(id)
            ...
    match inserted {
        Ok(_) => Ok(true),
        Err(sqlx::Error::Database(db)) if db.is_unique_violation() => Ok(false),
        Err(other) => Err(other.into()),
    }
}
```

La table `categories` porte deux contraintes uniques :

- `id uuid primary key` (globale) ;
- `categories_household_name_unique` sur `(household_id, lower(name))` (par foyer).

`is_unique_violation()` ne distingue pas laquelle est violée. Le handler `create_category` traduit systématiquement `Ok(false)` par :

```rust
// crates/server/src/categories.rs:87-88
Ok(false) => duplicate_category(), // "name: déjà utilisé dans ce foyer"
```

### Conséquences

1. **Message mensonger.** Si un client fournit un `id` déjà existant dans son propre foyer (collision UUID — extrêmement rare mais possible, ou recréation d'une entité supprimée), il reçoit une erreur sur le nom alors que le problème est l'`id`.
2. **Fuite d'existence cross-foyer théorique.** Un attaquant disposant d'un UUID cible (fuite par backup, log, etc.) peut créer une catégorie avec un **nom unique** dans son foyer mais l'`id` cible. S'il obtient un `422 "name: déjà utilisé"`, il sait que cet UUID existe dans la base, même s'il ne peut pas lire l'entité (isolation §9 préservée). La probabilité de deviner un UUID de 128 bits est négligeable, mais la primitive le permet.
3. **Incohérence avec les autres entités.** Payment methods et subscriptions retournent un `500` dans le même cas (voir F2) ; seules les catégories masquent la vraie nature de l'erreur.

### Recommandation

Avant l'insertion, vérifier si l'`id` fourni existe déjà pour ce foyer (ou globalement) et retourner une erreur `422` ciblant le champ `id`. Sinon, conserver le traitement actuel pour la contrainte de nom. Alternative : inspecter le message de contrainte violée dans `DatabaseError` pour distinguer `categories_pkey` de `categories_household_name_unique`, bien que la première option soit plus robuste face au renommage des contraintes.

## F2 — Payment methods / Subscriptions : `id` client déjà existant → `500`

### Description

Contrairement aux catégories, les repositories des moyens de paiement et des abonnements ne capturent pas les violations d'unicité :

```rust
// crates/storage/src/payment_methods.rs:43-51
pub async fn create(&self, actor: &Actor, id: Uuid, name: &str) -> Result<(), StorageError> {
    sqlx::query("insert into payment_methods (id, household_id, name) values ($1, $2, $3)")
        ...
        .execute(self.pool)
        .await?;  // <- unique violation remonte brute
    Ok(())
}
```

```rust
// crates/storage/src/subscriptions.rs:83-109
pub async fn create(&self, actor: &Actor, sub: &Subscription) -> Result<(), StorageError> {
    sqlx::query("insert into subscriptions ...")
        ...
        .execute(self.pool)
        .await?;  // <- idem
    Ok(())
}
```

Les handlers convertissent ensuite toute erreur `StorageError` en `500 Internal Server Error`.

### Conséquences

- L'isolation §9 est préservée : un `id` existant dans un autre foyer ne permet pas la lecture ou la modification.
- En revanche, un `500` pour une erreur de charge utile client est incorrect. Le client ne peut pas différencier une panne serveur d'un `id` déjà utilisé.
- C'est un cas d'erreur client légitime (retry après coupure, synchronisation rejouée) qui devrait retourner `422` avec le champ fautif.

### Recommandation

Uniformiser le comportement avec celui souhaité pour les catégories (F1 corrigé) : détecter la collision sur `id` et retourner un `422` ciblant le champ `id`, sans révéler l'appartenance au foyer.

## F3 — Tests `updated_at` : attente de 10 ms fragile

### Description

Les tests `modification_timestamp_is_server_provided` pour catégories et subscriptions insèrent un délai de 10 ms entre la création et la modification :

```rust
// crates/server/tests/categories.rs:609
// crates/server/tests/subscriptions.rs:831
tokio::time::sleep(std::time::Duration::from_millis(10)).await;
```

Puis ils vérifient `after > created_at`.

### Problème

- `tokio::time::sleep` est sensible au mode de runtime. S'il est jamais exécuté dans un contexte `start_paused = true`, le temps ne s'écoule pas et `now()` PostgreSQL peut ne pas avancer.
- Même en temps réel, 10 ms est une marge faible sur une machine CI chargée. PostgreSQL `now()` retourne le timestamp de début de transaction ; si les deux transactions démarrent dans la même milliseconde malgré le sleep, le test échoue.
- Le test des catégories vérifie en plus `created_at == updated_at` à la création. Cela repose sur l'évaluation unique de `now()` dans une commande `INSERT` — généralement vrai, mais non garanti si les colonnes sont peuplées par des `DEFAULT` distincts.

### Recommandation

Augmenter le délai à au moins 50–100 ms, ou mieux : utiliser `clock_timestamp()` dans la requête de test plutôt que `now()`, ou vérifier `after >= created_at` combiné à une différence explicite. Pour plus de robustesse, utiliser une assertion `after >= created_at` avec un delta minimal, ou une requête SQL `pg_sleep(0.05)` si l'isolation des tests `sqlx` le permet.

## F5 — Documentation OpenAPI 422 incomplète (information)

### Description

Les annotations `utoipa` des endpoints `createCategory`, `createPaymentMethod`, `createSubscription` indiquent « Nom invalide » ou « Validation par champ » pour le 422, mais ne précisent pas qu'un `id` invalide ou déjà utilisé peut aussi produire cette réponse.

### Recommandation

Mettre à jour les descriptions de réponse 422 pour mentionner le champ `id` (ex. « Identifiant ou nom invalide, ou identifiant/nom déjà utilisé »).
