## Résumé

L'implémentation respecte le garde-fou d'isolation par foyer (§9) : toutes les méthodes du repository filtrent par `household_id`, et les handlers traduisent systématiquement l'absence de ligne par un `404` générique, jamais `403`. Les 16 tests couvrent les deux critères d'acceptation de REQ-CAT-001 et les trois cas d'autorisation §9 pour chaque opération.

Aucune faille d'isolation critique n'a été trouvée. Les défauts relevés sont des angles morts de validation du nom, de normalisation, de cohérence du contrat OpenAPI et de couverture des cas limites.

## Findings

### CRITICAL

Aucun.

### HIGH

Aucun.

### MEDIUM

#### 1. Nom avec espaces de début/fin accepté et stocké tel quel

- **Fichiers** : `crates/core/src/category.rs:25-32`, `crates/server/src/categories.rs:57-69`
- **Défaut** : `Category::new` rejette les noms vides après `trim()`, mais **conserve** la valeur originale (espaces compris). Le handler `create_category` insère donc `"  Streaming  "` tel quel.
- **Scénario d'échec** : l'utilisateur saisit `" Streaming "` par inadvertance. La catégorie est créée avec succès, apparaît dans la liste avec ses espaces et peut coexister avec `"Streaming"`, violant l'esprit de REQ-CAT-004 (unicité par foyer, même en draft) et produisant un affichage incohérent.
- **Correctif** : normaliser le nom dans `Category::new` avec `let name = name.into().trim().to_string();` avant le stockage.

#### 2. UUID malformé renvoyé en `404` au lieu de `400`

- **Fichiers** : `crates/server/src/categories.rs:132-133`, `crates/server/src/categories.rs:175-176`
- **Défaut** : un identifiant de path invalide (`/categories/not-a-uuid`) est traité comme une ressource inexistante et retourne `404`.
- **Scénario d'échec** : un client buggy envoie un UUID tronqué ou mal encodé. Le `404` induit en erreur sur la nature du problème (ressource manquante vs. paramètre invalide) et complique le débogage côté intégrateur. Un `400` ne divulgue aucune existence car l'UUID n'est pas valide.
- **Correctif** : distinguer explicitement `Uuid::parse_str` en échec → `400 Bad Request` (avec un `Problem` générique), et `rows_affected() == 0` → `404`.

#### 3. Absence de contrainte d'unicité `(household_id, name)`

- **Fichier** : `crates/storage/migrations/0006_categories.sql:5-10`
- **Défaut** : la table `categories` n'a pas d'index unique sur `(household_id, name)`.
- **Scénario d'échec** : deux requêtes rapprochées créent `"Streaming"` pour le même foyer. Il en résulte deux catégories homonymes, rendant les statistiques et les sélecteurs d'UI confus. REQ-CAT-004 est en draft, mais l'absence de garde SQL laisse le comportement dépendre de la couche domaine uniquement.
- **Correctif** : ajouter `unique(household_id, name)` dans la migration (à fusionner avec REQ-CAT-004) ou documenter explicitement la décision de ne pas garantir l'unicité.

### LOW

#### 4. Aucun test pour UUID valide mais inexistant

- **Fichier** : `crates/server/tests/categories.rs`
- **Défaut** : les tests `authz_other_rename_category` et `authz_other_delete_category` vérifient l'accès à une ressource d'un autre foyer, mais aucun test ne vérifie le `PUT`/`DELETE` sur un UUID syntaxiquement valide et totalement inexistant dans le foyer de l'appelant.
- **Scénario d'échec** : régression future où le repository retournerait `false` pour une autre raison (ex. exception silencieuse) sans que le chemin "inexistant dans mon propre foyer" ne soit couvert.
- **Correctif** : ajouter deux tests `rename_nonexistent_category` et `delete_nonexistent_category` qui utilisent `uuid::Uuid::new_v4()` et attendent un `404`.

#### 5. Aucun test pour UUID malformé

- **Fichier** : `crates/server/tests/categories.rs`
- **Défaut** : les cas limites de path (`/categories/abc`, `/categories/`, `/categories/ `) ne sont pas testés.
- **Scénario d'échec** : une modification future du parseur ou de l'extracteur Axum pourrait changer le code retourné sans que la CI ne s'en aperçoive.
- **Correctif** : ajouter des tests pour `PUT` et `DELETE` avec un UUID malformé (statut attendu selon la décision du finding #2).

#### 6. Les réponses d'erreur ne sont pas vérifiées

- **Fichier** : `crates/server/tests/categories.rs`
- **Défaut** : les tests s'arrêtent au statut HTTP (`201`, `200`, `204`, `404`, `401`, `422`). Ils ne vérifient ni le `Content-Type: application/problem+json`, ni la structure RFC 9457 du corps, ni l'absence de détail révélateur.
- **Scénario d'échec** : une régression qui ferait fuiter un message d'erreur SQL ou une trace dans le corps `500` ne serait pas détectée.
- **Correctif** : ajouter un helper `assert_problem(response, status)` vérifiant le content-type et les champs `type`/`title`/`status`.

#### 7. Le contrat OpenAPI omet le `500 Internal Server Error`

- **Fichiers** : `crates/server/src/categories.rs:39-49`, `crates/server/src/categories.rs:80-88`, `crates/server/src/categories.rs:111-123`, `crates/server/src/categories.rs:157-167`
- **Défaut** : tous les handlers retournent `500` en cas d'erreur base de données, mais les annotations `utoipa::path` ne listent jamais cette réponse.
- **Scénario d'échec** : drift entre le contrat committé `api/openapi.json` et le comportement réel, potentiellement bloqué par `cargo xtask openapi --check` selon la rigueur de l'outil.
- **Correctif** : ajouter `(status = 500, description = "Erreur interne", body = wallos_proto::Problem, content_type = "application/problem+json")` à chaque opération.

### NIT

#### 8. Double responsabilité de `Category::new`

- **Fichier** : `crates/core/src/category.rs:20-33`
- **Défaut** : `Category::new` sert à la fois à construire une nouvelle catégorie (avec `Uuid::new_v4()`) et à valider un renommage (avec l'UUID existant). La signature est identique, ce qui est acceptable mais masque légèrement l'intention.
- **Scénario d'échec** : faible ; un refactoring futur pourrait ajouter une règle spécifique à la création (par ex. longueur max) et l'appliquer par mégarde au renommage.
- **Correctif** (optionnel) : introduire `Category::with_name(id, name)` pour le renommage, ou documenter que `new` est le seul point de validation du nom.

#### 9. Pas de limite de longueur sur le nom

- **Fichiers** : `crates/core/src/category.rs:25-32`, `crates/proto/src/lib.rs:188-192`, `crates/proto/src/lib.rs:196-200`
- **Défaut** : aucune borne supérieure n'est appliquée au nom. Un client peut envoyer un nom de plusieurs milliers de caractères.
- **Scénario d'échec** : affichage cassé dans l'UI, saturation de l'index `categories_household_idx`, ou déni de service léger sur les payloads JSON.
- **Correctif** : ajouter une validation de longueur maximale (ex. 100 caractères) dans `Category::new` et refléter `max_length` dans les schémas OpenAPI.

#### 10. Typo volontaire peu claire dans le test de renommage

- **Fichier** : `crates/server/tests/categories.rs:127`
- **Défaut** : la catégorie est créée avec le nom `"Musci"` puis renommée en `"Musique"`. La faute de frappe est probablement intentionnelle pour illustrer la correction, mais elle n'est pas commentée et peut être lue comme une erreur de revue.
- **Correctif** : ajouter un commentaire (`// nom volontairement erroné`) ou utiliser `"Old Name"` / `"New Name"`.

## Verdict

**Conditionnellement approuvé** pour l'objectif principal (isolation §9 + CRUD de base de REQ-CAT-001).

- **Isolation** : ✅ correcte — aucune méthode de repository sans `household_id`, aucun handler ne divulgue l'existence par un `403` ou un message différencié.
- **Validation du nom** : ⚠️ partielle — rejet du vide OK, mais absence de normalisation des espaces et de limite de longueur.
- **Chemins d'erreur** : ⚠️ le `500` est masqué (intentionnel), mais le `404` pour UUID malformé est sémantiquement incorrect.
- **Cohérence DTO** : ✅ les champs `CategoryDto`, `CreateCategoryRequest`, `RenameCategoryRequest` sont alignés.
- **Tests** : ✅ couvrent les critères d'acceptation et l'autorisation §9, mais laissent des angles morts sur les cas limites (UUID inexistant/malformé, corps des erreurs, espaces dans le nom).

**Recommandation** : corriger le finding MEDIUM #1 (normalisation du nom) et le #2 (UUID malformé → `400`) avant de considérer REQ-CAT-001 comme complètement close. Les findings LOW et NIT peuvent être traités dans un commit de suivi sans bloquer la fusion rétrospective.
