## Verdict global

**Requête de changements (RC).**

Le cœur métier est correct : les facteurs de conversion sont fidèles à `getPricePerMonth()` de Wallos 5.4.2, l'arithmétique `Decimal` est exacte, et les vecteurs de l'oracle correspondent à la formule. Toutefois, le scénario e2e ne respecte pas le protocole d'oracle `legacy` du §8.1 : il est couplé directement à `TargetDriver`, donc **non rejouable contre l'application d'origine**. Cela fragilise la chaîne de validation de l'oracle. De plus, le chemin `row_to_dto` contient un fallback mensonger (zéro silencieux sur montant négatif) et le repli `Money::zero` de `monthly_cost` est inutile.

## Traitement

- **F1 ⏳ DIFFÉRÉ (dette transverse §8.1-e2e).** Le point est **valide** mais **non spécifique à STA-001** : **tous** les specs e2e du dépôt (`subscription-create`, `subscriptions-list`, …) instancient `new TargetDriver(page, baseURL)` directement ; **aucun** n'injecte l'interface `AppDriver`. Rendre ce seul scénario rejouable contre `legacy` exigerait (a) que `LegacyDriver` implémente `subscriptionMonthlyCost` en **scrutant le DOM réel de Wallos** (structure/testids totalement différents), et (b) un refactor d'injection `AppDriver` — à appliquer **uniformément** à toute la suite, pas à un spec isolé (sinon incohérence). L'oracle STA-001 est par ailleurs capturé **authentiquement** en **exécutant le PHP de l'image pinnée** (précédent `REQ-SUB-012` : « vérifié en exécutant le PHP »), gelé et cité — la moitié « enregistrer depuis legacy » du §8.1 est donc satisfaite hors navigateur. Consigné comme **passe transverse dédiée** (refactor AppDriver-injection + méthodes LegacyDriver) dans `.hermes`.
- **F2 ✅ CORRIGÉ (cohérence/honnêteté ; cas en réalité inatteignable).** Dans `row_to_dto`, un `amount < 0` avec devise+cycle valides faisait échouer `Money::new` → `Money::zero` → `"0"` (contredisant le commentaire). Corrigé : la branche retombe sur `row.amount.to_string()` (montant brut), comme la branche par défaut ; appliqué **aussi** au `yearly_cost` (STA-002). **Nuance que kimi ignorait** : la migration `0008` impose `check (amount >= 0)`, donc un montant négatif **ne peut pas exister en base** — le correctif supprime l'incohérence et le commentaire mensonger, mais le chemin reste inatteignable (défense en profondeur). C'est pourquoi aucun test d'intégration ne peut l'exercer (le `CHECK` rejetterait l'insertion).
- **F3 ✅ CORRIGÉ.** Commentaire rectifié : le repli `unwrap_or_else(Money::zero)` est **purement mécanique** (satisfaction de R5 — `Money::new` ne peut échouer pour un résultat non négatif) ; il **ne prétend plus** avoir une sémantique métier et ne couvre pas l'overflow (propriété partagée par toute l'arithmétique `Decimal` du dépôt, hors périmètre).

## Points positifs confirmés

- **Facteurs fidèles à Wallos 5.4.2.** La fonction `getPricePerMonth()` de l'application d'origine utilise exactement les mêmes conventions : `30 / frequency` pour les jours, `4.35 / frequency` pour les semaines, `1 / frequency` pour les mois, `12 * frequency` pour les années, et `0` pour les achats one-time ([source Wallos `includes/list_subscriptions.php`](https://raw.githubusercontent.com/ellite/Wallos/v5.4.2/includes/list_subscriptions.php)).
- **Arithmétique `Decimal` correcte.** Les formules `price × 30 / interval`, `price × 4.35 / interval`, `price / interval`, `price / (12 × interval)` reproduisent fidèlement la sémantique capturée. L'utilisation de `Decimal::new(435, 2)` pour `4.35` est exacte, contraire au flottant PHP.
- **Oracle cohérent.** Les 9 vecteurs de `e2e/fixtures/oracles/REQ-STA-001-monthly.json` correspondent aux valeurs calculées par `monthly_cost` et à leurs arrondis d'affichage en EUR.
- **Cohérence DTO create/list dans le cas nominal.** `SubscriptionDto::from_core` (appelé par `from_core_derived` lors de la création/mise à jour) et `row_to_dto` (lecture liste) utilisent tous deux `monthly_cost_rounded`, ce qui garantit le même affichage.

## F1 — Le scénario e2e ne peut pas être exécuté contre l'application d'origine

### Description

Le scénario importe et instancie directement `TargetDriver` :

```ts
// e2e/specs/subscription-monthly-cost.spec.ts:6
import { TargetDriver } from "../drivers/TargetDriver";

// …
const app = new TargetDriver(page, baseURL!);
```

Or `AppDriver` — l'interface agnostique qui doit servir à la fois à `LegacyDriver` et `TargetDriver` (AGENTS.md §8.1) — ne déclare pas de méthode `subscriptionMonthlyCost` :

```ts
// e2e/drivers/AppDriver.ts
export interface AppDriver {
  // …
  subscriptionAmount(name: string): Promise<string>;
  deactivateSubscription(name: string): Promise<void>;
  // pas de subscriptionMonthlyCost
}
```

### Conséquences

1. **Protocole oracle non respecté.** Le §8.1 impose : écrire le scénario contre `AppDriver`, l'exécuter avec `TARGET=legacy`, l'enregistrer, puis l'exécuter avec `TARGET=app`. Ici, le scénario ne compile/runnerait tout simplement pas avec un `LegacyDriver`.
2. **Non-réversibilité de l'oracle.** L'oracle JSON est gelé, mais la suite de tests automatisée ne peut plus le re-valider contre Wallos si l'image de référence est remplacée ou si on suspecte une erreur de transcription.
3. **Perte du mécanisme de garde principal.** C'est précisément le dispositif qui empêche une IA de « réinventer » la règle métier ; le couper rend le gel de l'oracle moins crédible.

### Recommandation

- Ajouter `subscriptionMonthlyCost(name: string): Promise<string>` à `AppDriver`.
- Réécrire le test pour accepter une injection de driver (`{ app }: { app: AppDriver }`) afin qu'il puisse tourner avec `LegacyDriver` et `TargetDriver`.
- Vérifier que le scénario passe avec `TARGET=legacy` (l'application d'origine affiche-t-elle le coût mensuel exactement de la même manière ?) avant de le considérer comme preuve.

## F2 — `row_to_dto` retombe sur zéro pour un montant négatif

### Description

Dans `row_to_dto` :

```rust
// crates/server/src/subscriptions.rs:239-247
let monthly = match (CurrencyCode::new(&row.currency), cycle) {
    (Ok(currency), Some(cycle)) => {
        let price = Money::new(row.amount, currency).unwrap_or_else(|_| Money::zero(currency));
        wallos_core::stats::monthly_cost_rounded(price, cycle)
            .amount()
            .to_string()
    }
    _ => row.amount.to_string(),
};
```

Le commentaire dit : « Une ligne à la devise ou au cycle illisible retombe sur le montant brut (jamais un zéro silencieux). »

En réalité, si la devise et le cycle sont valides mais que `row.amount < 0` (données corrompues, migration ratée, etc.), `Money::new` échoue et on expose `"0"` — un zéro silencieux — au lieu du montant brut.

### Conséquences

- **Mauvaise dégradation.** Un abonnement corrompu masquerait son montant réel dans le champ dérivé, ce qui fausserait les totaux affichés et compliquerait le diagnostic.
- **Incohérence avec le fallback de la branche `_`**, qui expose bien `row.amount.to_string()`.

### Recommandation

Si `Money::new(row.amount, currency)` échoue dans la branche `(Ok(currency), Some(cycle))`, retomber sur `row.amount.to_string()` (comme dans la branche par défaut) au lieu de `Money::zero(currency)`.

## F3 — Le repli `Money::zero` dans `monthly_cost` est inutile

### Description

```rust
// crates/core/src/stats.rs:46-48
Money::new(monthly, currency).unwrap_or_else(|_| Money::zero(currency))
```

`Money::new` ne renvoie une erreur que si le montant est strictement négatif. Or `monthly` est le résultat de :

- `amount` ≥ 0 (garanti par `Money`),
- multiplication par `30`, `4.35` ou `1`,
- division par `interval` > 0 (garanti par `BillingCycle`).

Toutes les opérations conservent le signe positif. Le repli `Money::zero` n'est donc jamais déclenché pour un résultat négatif.

### Conséquences

- **Fausse sécurité.** Le commentaire affirme que le repli « évite seulement un `unwrap` (R5) » et qu'il est « jamais atteint ». C'est vrai pour les cas réalistes, mais le repli ne protège pas contre le seul échec arithmétique réaliste : un **overflow** de multiplication (par exemple un montant proche de `Decimal::MAX` multiplié par 30 provoque une panique avant même d'atteindre `Money::new`).
- **Complexité inutile.** La règle R5 interdit `unwrap`/`expect`, pas `unwrap_or_else`. Néanmoins, un commentaire indiquant « `Money::new` ne peut échouer ici car le résultat est toujours positif » serait plus honnête qu'un repli métier sans valeur.

### Recommandation

Soit clarifier le commentaire pour indiquer que le repli est purement mécanique (satisfaction de R5) et ne couvre pas l'overflow, soit — si l'on considère que `Money::new` ne peut jamais échouer ici — utiliser un `expect` documenté en production (mais cela viole R5). La solution la plus propre est de garder `unwrap_or_else` mais de ne pas prétendre qu'il a une sémantique métier.
