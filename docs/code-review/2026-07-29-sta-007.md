## Analyse détaillée

### 1. `filtered` suit le dernier filtre appliqué

```tsx
// frontend/ui/src/components/SubscriptionsList.tsx:35-37
const [filtered, setFiltered] = useState(false);
```

`filtered` n'est mis à jour que dans `load(...)` (ligne 59), c'est-à-dire **uniquement au montage** et **au clic sur « Appliquer »**. Les `onChange` des inputs (lignes 121, 127, 133) ne touchent que les états de saisie (`category`, `payer`, `state`), pas `filtered`. Cela garantit que l'indicateur reflète le **dernier filtre effectivement soumis au serveur**, pas un input non appliqué.

Le calcul (ligne 59) est cohérent avec la requête construite aux lignes 42-51 :

```tsx
setFiltered(cat.trim() !== "" || payerId.trim() !== "" || st !== "all");
```

- `cat` / `payerId` vides (après `trim()`) ou `st === "all"` → pas de filtre actif.
- N'importe quel critère non vide / non `all` → `filtered = true`.

#### Edge cases vérifiés

| Situation | Comportement attendu | Comportement constaté |
|-----------|----------------------|-----------------------|
| Montage initial | Aucun filtre | `load("", "", "all")` → `filtered = false` ✅ |
| Filtre état `active` appliqué | Indicateur affiché | `load(..., "active")` → `filtered = true` ✅ |
| Filtre état repassé à `all` | Indicateur masqué | `load(..., "all")` → `filtered = false` ✅ |
| Filtre catégorie ou payeur appliqué | Indicateur affiché | `filtered = true` ✅ |
| Erreur de chargement après changement de filtre | Indicateur inchangé, ancien total affiché | `setFiltered` non appelé dans la branche `else`, cohérent avec `setData` non appelé ✅ |

**Remarque** : le recalcul après sauvegarde (`save`, ligne 104) rappelle `load(category, payer, state)` avec les filtres courants, donc `filtered` reste cohérent.

### 2. Cohérence avec le total serveur

Le total affiché est `data.total.total` (ligne 172), qui est retourné par `GET /subscriptions` avec les mêmes paramètres de filtre que ceux utilisés pour calculer `filtered`. Il n'y a donc pas de décalage sémantique : l'indicateur textuel est affiché exactement quand la requête au serveur contenait un critère de filtre.

### 3. i18n en/fr

La clé `subscriptions.totalFiltered` est ajoutée dans les deux locales :

- `en.json` : `"totalFiltered": "(filtered set)"`
- `fr.json` : `"totalFiltered": "(ensemble filtré)"`

Utilisation correcte dans le composant (ligne 176) : `{t("subscriptions.totalFiltered")}`. Aucune chaîne en dur, conforme à REQ-I18N-002.

### 4. Tests — présence et absence

Les tests couvrent le **cas nominal** : absence initiale de l'indicateur, puis présence après application d'un filtre d'état `active`.

## F1 — Transition « filtre effacé » non testée

### Description

Aucun des deux tests ne vérifie que l'indicateur disparaît quand on repasse le filtre d'état à `all` (ou qu'on efface catégorie/payeur) et qu'on clique à nouveau sur « Appliquer ».

### Conséquence

Une régression future dans `load` (par exemple, un `setFiltered` qui ne serait plus mis à jour dans un certain chemin) pourrait passer inaperçue.

### Recommandation

Ajouter dans les deux tests une troisième phase :

```ts
await app.filterSubscriptionsByState("all");
expect(await app.totalIndicatesFiltered()).toBe(false);
```

## F2 — Filtres catégorie et payeur non testés pour l'indicateur

### Description

L'implémentation prend en compte trois critères (catégorie, payeur, état), mais les tests ne valident l'indicateur que via le filtre d'état.

### Conséquence

Un bug spécifique à la détection des filtres catégorie ou payeur (par exemple, une condition inversée ou une comparaison sans `trim`) ne serait pas détecté.

### Recommandation

Ajouter au moins un test vitest et un test e2e qui appliquent un filtre catégorie ou payeur non vide et vérifient que `subscriptions-total-filtered` apparaît.

## F3 — Scénario e2e couplé à `TargetDriver`

### Description

Le spec importe et instancie directement `TargetDriver` :

```ts
// e2e/specs/subscription-total-filtered.spec.ts:3
import { TargetDriver } from "../drivers/TargetDriver";
```

Et `AppDriver` ne déclare pas `totalIndicatesFiltered` ni `filterSubscriptionsByState`.

### Conséquence

Même si REQ-STA-007 est taggée `@design` (divergence assumée par rapport à Wallos), le scénario n'est pas écrit contre l'interface abstraite du §8.1. Cela empêche tout rejouage futur contre un `LegacyDriver`.

### Recommandation

Traiter en passe transverse : ajouter les méthodes à `AppDriver`, injecter le driver via une fixture, et réécrire le spec contre `AppDriver`.
