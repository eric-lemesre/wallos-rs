# ADR 0036 — Poussée locale : lot d'opérations indépendantes, idempotent, rejets par entité

- **Statut** : accepté (2026-08-06)
- **Contexte** : REQ-SYN-004 (« poussée des modifications locales »), `oracle: design`, criticality
  high, layer `[api, ui]`, e2e required, dépend de REQ-SYN-001 (id/horodatage) et REQ-SYN-006
  (idempotence). Contrepartie en écriture de la récupération incrémentale (SYN-003).

## Problème

Le client doit pousser un **lot** de modifications locales et **tolérer un rejeu** après coupure réseau.
Acceptation : (#1) un lot **rejoué à l'identique** mène au **même état final** qu'un envoi unique ; (#2)
un envoi **partiellement rejeté** identifie précisément les entités en échec, **les autres étant bien
appliquées**. À trancher : la granularité transactionnelle, la forme des opérations, et la stratégie
d'idempotence.

## Décision

### Endpoint `POST /sync/push`, opérations indépendantes

Le corps est `{ operations: [ { op: "upsert"|"delete", entity_type, id, payload? } ] }`. Chaque
opération est appliquée **indépendamment** (pas de transaction englobante), si bien qu'un rejet n'annule
pas les autres (critère #2). La réponse aligne **un résultat par opération** (`applied` / `rejected` +
motif). Un rejet est **fonctionnel** (type/opération inconnu, id d'un autre foyer, nom en doublon,
charge utile invalide, suppression d'un référencé), jamais une panne — celle-ci renvoie `500` sans
réponse mémorisée.

### Réutilisation des opérations existantes (aucun nouveau storage)

Un `upsert` **compose** les méthodes existantes : `create` puis, sur collision d'`id` (clé primaire
**globale**), `rename`/`update` **gardé par foyer** (§9) — un `id` appartenant à un autre foyer donne
`rejected`. Un `delete` réutilise les suppressions (transactionnelles, écrivant une pierre tombale
SYN-002). Aucune méthode de stockage nouvelle : la surface reste petite et déjà couverte.

### Double idempotence (critère #1)

1. **Par nature** : les upserts sont **clés par `id`** (client, SYN-001) — rejouer converge vers le même
   état ; les suppressions sont des **no-op** si l'entité est déjà absente (traitées `applied`).
2. **Au niveau du lot** : l'en-tête `Idempotency-Key` (REQ-SYN-006) mémorise la **réponse** ; un rejeu à
   clé + corps identiques la renvoie **sans réappliquer**. Sur panne d'infrastructure, la réservation est
   relâchée (`abort`) pour autoriser un nouvel essai.

## Conséquences

- Endpoint `pushSyncChanges` (`POST /sync/push`) : couverture API + authz 100 %. Aucun changement de
  schéma ni de repository.
- La suppression idempotente traite « entité déjà absente » comme **appliquée** (état voulu atteint),
  choix offline-first assumé ; seul un refus métier (référencé) est un rejet.
- Le **volet `ui`** est la capacité de poussée du client (client typé généré) ; l'appli web étant
  online-first (écritures directes), aucun composant UI dédié n'est ajouté — le parcours est exercé en
  e2e (`page.evaluate`). Cohérent avec OQ-009 (le natif offline est hors périmètre).
- Complète le duo pull/push. Reste REQ-SYN-005 (résolution de conflit : arbitrage last-write-wins +
  journal), qui s'appuie sur le même horodatage serveur.
